# UV-K1 接收链路核对

后续多槽收听切换按[四个判断](listening-paths.md)实施；本页保留单路接收排查记录。

2026-10-19。范围为 BK4829 NFM 接收、静噪、音频路由，以及相关校准和调谐。代码一致性和寄存器模型通过不等于实机语音验收通过。

## 参考版本

- [F4HWN，5fedc09e](https://github.com/armel/uv-k1-k5v3-firmware-custom/tree/5fedc09e9ddec350823adb9bb2d81df05b52ab8d/App)：`driver/bk4829.c`、`radio.c`、`settings.c`、`app/app.c`、`app/spectrum.c`、`driver/gpio.h`。
- [ApeX，41cc768d](https://github.com/N7SIX/UV-K1Series_ApeX-Edition_v7.6.0/tree/41cc768d946bff97db691ee372b4dbf9bc46743e/App)：同名射频、设置与音频实现。

## 对照结果

| 链路 | 参考实现 | 本项目及本次处理 |
| --- | --- | --- |
| 启动调用链 | `main → BK4819_Init → SETTINGS_LoadCalibration → RX setup` | **生产代码只有 `RADIO_Init → loadSelected → 部分 RX setup`，完全漏调 `RECEIVER_Init → RX_DEVICE_Init → BK4819_Init`**。本次实机读回揭示此缺陷；已在 `RADIO_Init` 首先调用幂等接收初始化，补上控制器启动顺序回归 |
| 三线总线 | PF9 / PB8 / PB9，读取时 SDA 转输入，下降沿期间采样 | 接线、位序、读写方向一致；K1 使用至少 1 µs 延时。REG_30 使用请求值缓存，诊断会明确标注 |
| 上电与接收 | REG_37 初始化 `9D1F`，RX `9F1F`；REG_30 `0000 → BFF1` | 已匹配。REG_36 固定 0、PA gate 关闭是本项目接收专用策略 |
| 参考时钟微调 | 从校准 `0x188` 读 s16，REG_3B = `22656 + trim`，范围 ±1000 | **原先完全缺失，现已补齐**；本机备份 trim = −2，预期 REG_3B = `587E`；不改 REG_3C |
| 音频增益 | 校准 `0x18E/18F` 为 AF/DAC 增益，非法值回退 58/8 | **原先固定 58/8，现加载原厂值**；本机 44/14，校准后 REG_48 = `B2CE`。随后 FM 模式按参考把 DAC 设为 15，变为 `B2CF`，AF 增益仍为 44 |
| FM 解调 | REG_31 bit 0 清零；42=`6B5A`、2A=`7400`、2B=0、2F=`9890`、54=`9009`、55=`31A9`、3D=`2AAB`；AFC 开 | 上一提交已补齐，本次加入真实驱动寄存器模型回归；不会给 K1 写 K6 的 REG_3C 配置 |
| AGC | 10–14=`0318/033A/03DB/03DF/0210`、49=`2AB2`、7B=`73DC`、7E=`303E` | 自动增益路径已匹配；K1 的 AFC 通用调参入口保持不覆盖参考配置 |
| 接收滤波 | 6.25 / 12.5 / 25 kHz 信道间隔的预设分别为 `2058/4048/3028` | 已匹配。项目显示 6/12/26 kHz 是名义标签，不能解释为实测 −3 dB 带宽 |
| 静噪阈值 | 174 MHz 以下读 `0x60`，以上读 `0x00`；采用参考启用的灵敏度变换 | 六行校准与变换已匹配。**修复快速调频跨 174 MHz 时仍使用旧表** |
| 静噪时间 | REG_4E open=5、close=3、bit8=1 | 已匹配，本次回归验证组合值。后续改为用户可调，Auto 取 5／3；补齐初始化后用户实测 1／1 也不跳 |
| 静噪状态 | REG_02 LOST 开、FOUND 关，由 REG_0C bit0 驱动读取 | 已使用共享事件泵，避免与 CTCSS/DCS 互相消费事件。**补齐每次 K1 调谐前清理旧事件与旧开门状态** |
| 调谐重启 | 参考普通接收和频谱调谐都将 REG_30 清零再恢复 | **原先复用 K6 的 `0200 → 原值`，现 K1 改为 `0000 → 原值`**；保持静音扫描的 DAC 位，K6 路径不变 |
| 静噪为 0 | SQ0 / Monitor 不以硬件静噪状态限制音频 | **原先仍强制要求硬件开门，现 SQ0 显式绕过 carrier 状态**；配置接收亚音时仍要求亚音匹配，搜台仍使用临时非零静噪 |
| 音频门控 | 正常接收静噪变化不反复关闭 AF DAC；PA8 控制功放 | **原先每次关门都关闭 DAC，现 K1 保持 DAC 运行**，明确写 AF `6142/6042`，关门先关功放。后台准备和跨芯片路由仍能关闭 DAC，避免混音 |
| CTCSS / DCS | REG_51=`9040` / `A033`；CTCSS 换算 2.06488，DCS 控制字 2775 | 已匹配；本次回归覆盖 67 Hz 和 DCS 配置，不代表解码灵敏度已实测 |
| BK1080 共用前端 | 广播 FM 需要 BK 的 VHF LNA，停止双守候 | 项目已有板级能力及互斥约束；本次未改广播驱动 |

最关键的确定缺陷是接收初始化从未被生产启动流程调用：此前补齐的初始化寄存器并未真正执行，编译器甚至从镜像中移除了这条不可达链路。第一次刷入并读回时，REG_1F=`5454`、3B=`5880`、3D=`0000`、48=`338F`、7E=`302E`，与初始化预期不符；物理 `0x10188` 校准读取则与备份完全一致。用户确认在另一台对讲机按 PTT 后仍只有哒哒声。因此第一次刷机不能算修复通过。补齐启动调用后第二次刷机，1F/3B/48/7E 等配置读回符合预期，用户确认语音清晰且哒哒声消失。这些结果支持启动漏调为本次主要原因；本次同时有其他接收修正，未做逐项回退的单变量实验。更早的「静噪一直跳」同样发生在初始化漏调期间，当时按参考改为 5／3 延时后不再跳；补齐初始化后用户用 1／1 实测接收正常、不跳，因此延时过短不是该现象的成立原因。

## 有意保留的差异及未实现项

- RF 前端分界仍由项目设置选择 240 / 280 MHz，默认 240；参考 K1 固定 280 MHz。145 / 435 MHz 接收不受该差异影响，240–280 MHz 的前端选择需按 280 设置验证。
- 无接收亚音时，本项目关闭 REG_51 的亚音功能；参考仍配置 55 Hz 尾音检测。尾音消除尚未实现，可能影响通话结束的噪声，不应据此宣称能解决持续无语音。
- VOX、压扩、扰频和 DTMF 接收未作为当前 K1 接收功能开放；参考有相应配置流程。当前从芯片软复位进入普通 NFM，不能把这些设置菜单视为已支持。
- AM、USB/RAW/BYP 等解调模式、K1 发射、USB CDC、配置/频道持久化均不在本次补齐范围。AM 与发射保持能力禁用；外部 Flash 仍只有读取路径，不写入或擦除原厂校准扇区。
- 本项目的多槽守候不是参考的双 VFO 调度；语音验收先以单槽完成，再验证多槽、搜台、频谱返回后的恢复，不能用主机模拟代替实际时序验收。

## 验证与实机步骤

`tests/bk4829-rx-regression.c` 使用真实 BK 初始化、模式、调谐和静噪驱动，验证参考寄存器值、校准边界、旧事件清理及 K6 分支。上层测试覆盖 174 MHz 跨表、SQ0、接收亚音与 K1 音频门控。`tests/run.sh` 同时运行原有接收、守候、存储及协议回归；构建必须包含 `make BOARD=uvk1` 与 `make BOARD=uvk6`。

新增 `tools/resources.py --port PORT rf`，通过带时间戳的固定命令 `0x0576/0577` 读取白名单寄存器；不提供任意寄存器写入，不读取会消费事件的 REG_02 或 FIFO。REG_30 显示请求值缓存，其余为逐个读取，不是同时采样。

刷入后正常开机：

1. 单槽、145 / 435 MHz 已知语音源、NFM、接收亚音 Off，先测 SQ0，再测 SQ1/4；分别记录语音、底噪、绿灯与哒哒声。
2. 读 `rf`，核对 REG_3B=`587E`、REG_48=`B2CF`、REG_47 开门 `6142` / 关门 `6042`、FM 配置、RF 频率字、静噪阈值和 REG_3F mask。保持 NFM 接收时，REG_30 的 DAC 位应在关门后仍为 1。
3. 有稳定信号时连续读 `stats`，记录 `squelch_changes` 的增量。计数不是声音测量，RSSI 高也不能证明 FM 已正确解调。
4. 测接收亚音、174 MHz 跨表、广播 FM 往返、守候及扫描返回。

刷机页 ACK、应用 UART 应答、寄存器读回和人耳语音验收应分别记录，不能合并成一句“实机通过”。
