# UVK6 Reborn 硬件事实与验证记录

记录日期：2026-10-10。源码基线：`ea18356`，加工作区中的 I²C 修复。本文用于开发和故障排查，不是经过测量验证的整机规格表。

## 证据范围

本文区分三类信息：

- **实机确认**：本次串口通信、刷机日志及用户反馈直接支持的结论。
- **源码定义**：固件的目标、引脚和存储约定，尚不等于拆机确认的电路。
- **待确认 / 推测**：缺少芯片丝印、原理图、完整存储备份或测量证据。

不能仅凭项目名称确认某一台机器的 MCU、EEPROM 型号或改装方案；也不能仅凭编译成功认定所有硬件功能兼容。

## MCU 与固件内存布局：源码定义

项目面向 DP32G030 平台，构建参数为 ARM Cortex-M0、Thumb、AAPCS。寄存器定义位于 `src/inc/dp32g030/`。尚未通过本台设备芯片丝印独立确认 MCU 型号。

[链接脚本](../firmware.ld) 定义：

| 区域 | 起始地址 | 固件允许使用的大小 |
| --- | --- | --- |
| 应用 Flash | `0x00000000` | 60 KiB |
| RAM | `0x20000000` | 16 KiB |
| 栈顶 | `0x20004000` | RAM 末尾 |

这些是构建约束，不能据此推断整片 Flash 容量和 Bootloader 的实际地址。最后一次编译报告 Flash 使用 59,256 B、RAM 使用 10,792 B；RAM 数字包括链接时预留部分，不是运行时堆栈峰值测量。

## 外设与 GPIO：源码定义

主要依据：[GPIO 名称](../src/driver/gpio.h)、[引脚复用初始化](../src/board.c)、[键盘扫描](../src/driver/keyboard.c)。下表为固件预期映射，未经本台 PCB 通断测量。

| 功能 | MCU 引脚 | 备注 |
| --- | --- | --- |
| UART1 TX / RX | PA7 / PA8 | 刷机及应用串口所用配置 |
| I²C SCL / SDA | PA10 / PA11 | 软件 I²C，与键盘扫描输出行共用 |
| 键盘扫描输入 | PA3、PA4、PA5、PA6 | 对应四列输入 |
| 键盘扫描输出 | PA10、PA11、PA12、PA13 | PA12 / PA13 还被命名为语音芯片引脚 |
| PTT | PC5 | 按下读取为低电平 |
| LCD 背光 | PB6 | GPIO 控制；亮度实现见背光驱动 |
| LCD SPI 片选 / 时钟 / 数据 | PB7 / PB8 / PB10 | SPI0 的 SSN / CLK / MOSI |
| LCD A0 / 复位 | PB9 / PB11 | 驱动面向 ST7565，画面尺寸定义为 128×64 |
| SWD 数据 / 时钟 | PB11 / PB14 | PB11 与 LCD 复位复用 |
| BK4819 控制总线 | PC0 / PC1 / PC2 | SCN / SCL / SDA，区别于 PA10 / PA11 的 I²C |
| 手电筒 | PC3 | GPIO 控制 |
| 音频路径控制 | PC4 | 接收音频路由 |
| BK1080 控制 | PB15 | 某些改装接收路径也使用相关控制逻辑 |
| 电池 ADC | PA9 / PA14 | 配置为 ADC CH4 / CH9，代码分别读取为电压 / 电流原始值 |

红、绿指示灯通过 BK4819 的 GPIO 控制，代码分别使用 `BK4819_GPIO5_PIN1_RED` 和 `BK4819_GPIO0_PIN28_GREEN`，不是上表 MCU 的直接 GPIO。指示灯状态受外设初始化及 Bootloader 行为影响。

由于键盘与 I²C 共用 PA10 / PA11，键盘轮询会改变这些引脚的输出状态。维护驱动时必须一起检查 GPIO 方向、输入使能、开漏配置及总线空闲状态。

## 接收与发射路径：源码定义

固件具有 `BK4819`、`BK1080`、`SI4732` 三种无线电上下文。存在驱动不代表本台机器装有全部芯片。

- BK4819 是此固件实现收发操作的主要路径。
- BK1080 驱动用于广播接收路径。
- SI4732 路径面向安装对应硬件的设备；本次未独立验证本台是否安装、如何接线以及实际接收能力。
- SI4732 的 SSB 接收依赖补丁。菜单中出现 `LSB` / `USB` 不足以证明硬件和补丁已就绪。

本次没有完成 RF 功率、频率误差、灵敏度、滤波边界、天线或发射校准测量。菜单功率档位不能视作固定瓦数。接收 / 发射频率能力须另行验证。

## EEPROM：物理容量与软件布局必须分开

### 源码中的容量表

依据：[设置定义](../src/settings.h)、[容量和页表](../src/settings.c)、[EEPROM 驱动](../src/driver/eeprom.c)。

| 固件类型名 | 配置容量 | 配置写入分页大小 |
| --- | --- | --- |
| BL24C64 | 8 KiB | 32 B |
| BL24C128 | 16 KiB | 64 B |
| BL24C256 | 32 KiB | 64 B |
| BL24C512 | 64 KiB | 128 B |
| BL24C1024 | 128 KiB | 128 B |
| M24M02 | 256 KiB | 256 B |
| 4Mbit | 512 KiB | 128 B，代码注明为保守写入块大小 |

**本台 EEPROM 型号、容量和物理页大小尚未确认。** 类型名称来自软件表，不能代替芯片丝印和实际地址映射验证。

当前探测通过扫描 `0xA0`、`0xA2` … `0xAE` 的应答数量推断类型：1 个 → BL24C64，2 个 → BL24C128，4 个 → M24M02，8 个 → 4Mbit，其他 → UNKNOWN。这些是含读写位的 8 位地址形式；对应 7 位地址为 `0x50`～`0x57`。

应答数量不能唯一确定器件容量。驱动还假设每个 64 KiB bank 使用一个对应地址，并发送两字节内部地址。必须验证实际器件的寻址方式，不能把上述推断作为已确认的芯片规格。表中定义的其他容量也不意味着当前探测能准确识别它们。

### 当前项目的软件布局

| 内容 | 地址 / 规则 |
| --- | --- |
| 格式标识 | 地址 0 起，四字节 `UVR1` |
| 设置结构 | 地址 4 起，长度为 `sizeof(Settings)` |
| 频道记录 | 紧随设置结构，每条长度为 `sizeof(CH)` |
| 设置签名 | `checkbyte` 使用 `0x15` |
| Hawk5 SSB 补丁 | 代码使用 8,840 B 的补丁，预期位于所选 EEPROM 末尾 |

设置、频道使用 C 结构和位域保存。编译布局及结构变更都可能影响存储兼容性，不能把任意其他固件的 EEPROM 内容直接解释为本项目结构。

新版启动会识别格式标识并校验设置；未认可的配置进入初始化界面。EEPROM 写入默认锁定，读取到有效配置或用户明确初始化后才启用。

新版初始化通过 `0` → `1` 确认，重建本项目设置和频道，**不是整片 EEPROM 写成 `0xFF`**。补丁及其他区域的保留 / 兼容性仍需按实际地址布局核查。

## I²C 卡顿问题：已发现代码缺陷，效果待测量

`BOARD_PORTCON_Init()` 关闭了 PA10 输入缓冲，而 `scl_hi_wait()` 又读取 SCL 并等待其变高。工作区修复在 `I2C_Init()` 中重新启用 PA10 输入缓冲，同时修正等待循环的超时判断。

等待循环上限为 10,000 次，每次延时 1 μs。若 SCL 读值一直低，每次调用可能造成约 10 ms 额外等待；EEPROM 读写会多次调用，从而阻塞主循环和按键轮询。

这是有源码依据的卡顿原因候选，不是已测量的本台唯一根因。本次恢复同时更新了启动 / EEPROM 处理，未分别进行对照实验，不能把恢复效果全部归因于 I²C 修复。

右上角芯片图标由 `gEepromWrite` 触发，表示近期写入活动；图标闪烁不能单独证明正在反复读取、存储布局不兼容或 EEPROM 芯片损坏。

## 刷机协议与本次恢复记录

本次成功恢复使用 UART 配置 38,400 baud、8 数据位、无校验、1 停止位。该配置在本次通信有效；应用驱动的波特率寄存器计算见 [UART 驱动](../src/driver/uart.c)，其分频常量为 `39053U`。

协议包具有 `AB CD` 帧头、长度字段、混淆数据和 `DC BA` 帧尾。Bootloader 握手命令为 `0x0518`，固件块写入命令为 `0x0519`，块确认命令为 `0x051A`。恢复脚本按 256 B 分块发送，最后一块使用实际长度，并检查确认中的块地址。

本次使用原始 `firmware.bin` 成功写入；打包文件 `firmware.packed.bin` 不能据此认定适用于同一工具。

原 k5prog 在本机出现过串口设置错误、帧头失步和首块无确认。临时 Python 恢复脚本最终完成所有块确认，但尚未定位旧工具失败的全部原因。不能把“换脚本后成功”扩大为特定 USB 芯片或整个工具的普遍兼容结论。

关键经过：

1. 首次刷入后，用户报告按键迟缓、芯片图标闪烁。
2. 后续多次刷机未收到首块确认，期间用户报告黑屏、背光和灯无反应。
3. 黑屏状态下仍取得 Bootloader `3.00.02` 的有效握手。
4. 通过按帧解析的恢复脚本成功写入全部 59,256 B。
5. 用户确认重新亮起，并提出旧固件 EEPROM 布局不兼容的解释。

旧布局导致启动异常是合理推测，尚缺旧 EEPROM 备份进行验证。此前失败是否擦除 / 部分写入首块也未回读确认；无确认不等于没有修改 Flash。不能将这些推测记录为已经证明的故障链。

本次成功恢复的临时脚本和日志曾位于 `/tmp/uvk6-recover.py`、`/tmp/uvk6-recover.log`；它们未纳入仓库，可能被系统清理。本文记录必要结果，不能替代完整的可复现工具和原始日志。
